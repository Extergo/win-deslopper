# Product principles

1. Trust before feature count; stable systems matter more than aggressive debloating.
2. Reversibility before convenience. Inspect, explain, and require one deliberate Apply action; safety after authorization comes from bounded execution, capture, verification, and rollback.
3. Use precise language, supported mechanisms, and explicit build compatibility instead of hype or universal claims.
4. Users must understand what changes, why, likely impact, verification, and rollback.
5. Do not call every Windows component malware or adware, promise vague optimisation, or use dark patterns.
6. Local safety functionality must remain useful when a backend is unavailable.
7. Paid status never weakens compatibility, verification, or rollback requirements.
8. Preview state must never be presented as completed system work.
9. Unknown, permission-limited, failed, not applicable, and absent are distinct; uncertainty is not a health score.
10. Inspection-only components must stay useful without implying that an executor exists; actionable components must map to an exact registered operation.
11. Diagnostics are user-reviewed, allowlisted, redacted, local-only, and never uploaded automatically.
12. Experimental target approval ceremony is engineering tooling, not normal product authorization.
